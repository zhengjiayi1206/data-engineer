# 实时数据管道设计

```text
订单/评价/物流服务 -> OLTP + 事务 Outbox -> CDC/消息队列
                                         |-> 订单状态处理 -> 查询库/缓存 -> 卖家后台
                                         |-> 评价队列 -> 规则分流/LLM -> 结果库 -> 后台
                                         |-> 物流状态 -> 延迟定时检查 -> 去重告警 -> 卖家
                                         `-> 明细归档 -> OLAP 明细与日聚合 -> 六个月曲线
```

OLTP 保存订单权威状态，业务更新与 outbox 同事务写入，避免先写库后发消息丢失；CDC 将消息推到队列。订单消费者依据事件 ID 和订单版本幂等处理，过期事件不能覆盖较新状态。查询库按卖家和订单组织，缓存热点状态，更新时失效或刷新。需要对租户做鉴权，避免卖家读取他人数据。延迟预算从业务提交成功开始计时，监控 P95/P99；目标为 30 秒内可见，超限告警并可回查 OLTP。落后时页面提示数据更新时间。

评价进入独立队列，不阻塞订单链路。空文本和模糊短评直接标记信息不足，明确的简单内容可由规则处理，其余批量送模型。任务包含版本、结果状态和截止时间，校验 JSON 与原文证据；失败有限重试并进入人工队列。60 秒包括排队和处理，需监控积压、设置并发及优先级；外部模型不可用时不承诺总能在一分钟完成，应告警并展示待处理状态。

物流异常不能仅靠新事件触发：到预计送达时间时，定时任务重新读取当前状态，对未送达订单产生告警；按订单、异常类型和状态版本设置幂等键与冷却时间。延迟送达门槛、时区和通知渠道需业务确认。任务失败需重试并定期扫漏，避免重复或漏报。

历史明细可归档对象存储，OLAP 保存按卖家、日期分区的明细和预聚合，六个月曲线优先读取聚合。毫秒级响应是目标，需要根据卖家数量、并发、指标和数据量进行压测；聚合重算及迟到数据需版本化。消息队列用于削峰和重放，不作为长期权威数据库。10 万订单/天约 1.16 单/秒，100 万约 11.6 单/秒是日均而非峰值；初期可使用托管队列与数据库物化汇总，规模增长后再按峰值和延迟引入独立流计算与 OLAP 集群。

成本示例仅作假设：若 100 万订单/天、每单均一条评价、每条平均模型成本 $0.001，则一年约 $365,000，未计重试及基础设施；真实成本取决于评价率、模型价格和 token，必须使用当前报价重新测算。通过有效文本过滤、批处理、缓存、模型分级、每卖家和全局额度降低费用；达到预算时停止非关键任务并进入待处理队列。

主要风险：一是重复、乱序或丢消息，采用 outbox、幂等、版本和重放，并每日与 OLTP 对账；二是模型超时、误抽和费用失控，采用证据校验、预算封顶、限流及人工复核；三是延迟和聚合不一致，监控端到端延迟与对账差异，补算迟到事件。所有服务均需监控队列堆积、死信、查询延迟及告警投递成功率。
